### 3.1 U1 落地约束

- Activity 增加可空字段 deletedAt；删除接口只设置该字段，不执行物理 DELETE。
- 学生端活动列表、详情、报名入口统一过滤 deletedAt IS NULL；管理员端可查看“已删除”并恢复（恢复是否做由实现阶段决定，不阻塞编码）。
- 已删除活动不再接受新报名；历史 Registration 与 Message 保留，C9 统计只统计未删除活动。
- 不级联删除报名和通知；避免破坏历史数据。

### 3.2 U3 落地约束

- 报名/审批事务开始时，先对目标 Activity 行执行 SELECT ... FOR UPDATE；拿到锁后再统计已通过人数。
- 直接报名与审批使用相同锁顺序，避免两个事务交叉等待。
- 并发失败按业务结果处理：名额已满、状态已变化；不做自动重试循环。
- 不引入分布式锁；单机数据库行锁满足课程范围。

### 6.3 已知差异与未做项

- 设计类图元素 RegistrationPolicy.decide 的参数与实现不同；实现更窄，未改变“策略只决定准入”的职责。
- 设计文档曾写“容量由服务统一校验”；实现把提交准入判定放进策略，服务保留锁、统计和审批复查。该差异已在《设计模式决策报告》2.4 说明，属于可讨论取舍，不隐藏。
- 活动恢复（撤销软删除）未实现；若课程要求“可恢复”，需新增端点、前端入口与测试，不能只靠数据库改字段。
- 通知无幂等键、无 outbox、无故障注入测试；“不会因重试重复”只成立于当前不重试 + 状态机防重，不等于“任何情况下不重复/不丢失”。
- 未做 MySQL 专项 C1—C10、未做高并发压测、未做前端自动化；这些是 baseline-v1 的已知缺口，CR 阶段按需补。
