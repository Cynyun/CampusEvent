# CampusEvent 用例说明（设计 V1）

**项目**：校园活动报名与管理系统（CampusEvent）  
**阶段**：初始版本设计，对应 Git 标签计划 `baseline-v1`  
**范围**：P2-F01—P2-F08；不含教师后续发布的需求变更  
**图形版本**：[用例图](diagrams/use-case.drawio.svg)（draw.io 源文件见 `diagrams/CampusEvent-design.drawio`）

## 1. 参与者

| 参与者 | 说明 |
|---|---|
| Student（学生） | 浏览活动、报名、取消报名、查看站内通知 |
| Admin（管理员） | 创建/编辑/删除活动、审批报名、查看活动统计 |

采用固定演示账号，不实现注册、复杂权限与多角色授权。

## 3. 核心用例说明

### UC-01 创建活动

- **前置条件**：管理员已登录；活动名称、类型、时间、地点、人数上限、报名方式已填写。
- **触发**：管理员提交“创建活动”。
- **基本流**：
  1. 系统校验必填字段、容量为正整数、时间与地点格式合法。
  2. 系统创建 `Activity`，保存 `policyType`（DIRECT 或 APPROVAL）。
  3. 返回创建成功，活动出现在列表和统计中。
- **扩展流**：
  - E1 容量 ≤ 0：拒绝保存，提示“人数上限必须为正整数”。
  - E2 必填字段缺失或时间格式错误：拒绝保存，保留已填内容。
- **后置条件**：活动持久化；此时尚未产生报名，不发送通知。
- **业务规则**：活动开始后不得新增报名；创建时允许设置未来开始时间。

### UC-04 直接报名

- **前置条件**：学生存在；活动存在且 `policyType=DIRECT`；当前时间早于活动开始时间；该学生没有同活动的“待审核/已通过”有效报名。
- **触发**：学生在活动详情页点击“报名”。
- **基本流**：
  1. 系统加载活动与学生，检查活动未开始、未满员。
  2. 系统查询该学生在该活动下的有效报名，确认不存在重复。
  3. 系统统计“已通过”报名数，执行公共服务规则：`approvedCount < capacity`。
  4. `RegistrationPolicy` 返回 `APPROVED`。
  5. 系统创建状态为“已通过”的 `Registration`，提交事务。
  6. 事务提交后发布 `RegistrationApproved` 事件；`InAppNotificationObserver` 写入站内消息。
  7. 返回报名成功。
- **扩展流**：
  - E1 已存在“待审核/已通过”报名：拒绝，提示“请勿重复报名”。
  - E2 已满员：拒绝，提示“名额已满”。
  - E3 活动已开始：拒绝，提示“报名已截止”。
  - E4 通知写入失败：记录错误日志；报名记录仍保留，事务不回滚。
  - E5 并发报名导致容量竞争：事务开始对 Activity 行 SELECT ... FOR UPDATE，再重新统计；失败方按 E2 处理。
- **后置条件**：存在一条“已通过”报名；名额统计增加；产生一条站内通知。
- **业务规则**：名额只按“已通过”计算；待审核不占名额。

### UC-05 申请审核型报名

- **前置条件**：学生存在；活动存在且 `policyType=APPROVAL`；当前时间早于活动开始时间；无同活动有效报名。
- **触发**：学生在审核型活动详情页点击“申请报名”。
- **基本流**：
  1. 系统加载活动与学生，检查活动未开始。
  2. 系统检查重复有效报名。
  3. `RegistrationPolicy` 返回 `PENDING`；不执行名额扣减。
  4. 系统创建“待审核”报名，提交事务。
  5. 发布 `RegistrationSubmitted` 事件，写入“已提交，等待审核”站内消息。
  6. 返回申请成功。
- **扩展流**：
  - E1 存在有效报名：拒绝重复申请。
  - E2 活动已开始：拒绝。
  - E3 活动已满员：仍允许提交“待审核”（待审核不占名额），但审批时按 UC-07 重新检查容量；这是本设计采用的规则。
  - E4 通知失败：记录日志，不回滚报名。
- **后置条件**：存在一条“待审核”报名；不改变已通过人数；产生提交通知。
- **业务规则**：待审核报名暂不占用名额；同一学生同一活动只能有一条有效报名。

### UC-06 取消报名

- **前置条件**：学生存在；报名存在且属于该学生；状态为“待审核”或“已通过”。
- **触发**：学生在“我的报名”或活动详情页点击“取消报名”。
- **基本流**：
  1. 系统校验报名归属与学生身份。
  2. 校验当前状态为“待审核”或“已通过”。
  3. 将状态改为“已取消”，记录更新时间。
  4. 发布 `RegistrationCancelled` 事件，写入站内消息。
  5. 返回取消成功；统计同步减少“已通过”或“待审核”数量。
- **扩展流**：
  - E1 报名不属于当前学生：拒绝，按 404/无权限处理。
  - E2 状态已是“已取消/已拒绝”：拒绝重复取消。
- **后置条件**：原记录保留为历史；允许该学生再次申请同一活动。
- **业务规则**：指导书只限制“活动开始后不允许新增报名”，未禁止取消；本设计不额外增加取消时间限制。

### UC-07 审批报名

- **前置条件**：管理员已登录；报名存在且状态为“待审核”。
- **触发**：管理员在待审核列表点击“批准”或“拒绝”。
- **基本流（批准）**：
  1. 系统加载报名与活动，校验状态仍为“待审核”。
  2. 统计该活动“已通过”人数，再次检查 `approvedCount < capacity`。
  3. 将状态改为“已通过”，提交事务。
  4. 发布 `RegistrationApproved` 事件，写入审批结果站内消息。
  5. 返回批准成功。
- **基本流（拒绝）**：
  1. 校验状态为“待审核”。
  2. 将状态改为“已拒绝”，提交事务。
  3. 发布 `RegistrationRejected` 事件，写入站内消息。
- **扩展流**：
  - E1 报名已不是“待审核”：拒绝操作，提示状态已变化。
  - E2 批准时名额已满：批准失败，状态保持“待审核”，不超容量。
  - E3 并发批准导致最后一个名额竞争：事务开始对 Activity 行 SELECT ... FOR UPDATE，再重新统计；只有一个成功，另一个按 E2 处理。
  - E4 通知失败：记录日志，不回滚审批结果。
- **后置条件**：状态变为“已通过”或“已拒绝”；统计同步；产生站内通知。
- **业务规则**：批准时必须再次检查名额；待审核不占名额。

## 4. 其余用例（简表）

| 编号 | 基本流摘要 | 关键扩展 |
|---|---|---|
| UC-02 编辑/删除活动 | 管理员修改活动字段；删除采用软删除（写 deletedAt，不物理删除），有报名也允许软删除 | 已有报名、活动已开始、容量改小导致已通过人数超限、已删除活动不再接受新报名 |
| UC-03 浏览与筛选活动 | 学生查看列表/详情，按名称筛选 | 无匹配结果、活动已开始、活动已删除 |
| UC-08 查看站内通知 | 学生查看自己的消息列表，标记已读 | 无消息、消息属于他人 |
| UC-09 查看活动统计 | 管理员查看已通过数、待审核数、剩余名额 | 活动不存在、无报名 |
