# CampusEvent 需求变更影响分析（CR-01 / CR-02）

- **分析基线**：`baseline-v1`，提交 `46b5c3f`
- **分析日期**：2026-11-26
- **当前状态**：分析阶段结论已保留；CR-01/CR-02 已在 `change-v2` 实施，实际结果见第 9 节“实施后记”
- **变更范围**：CR-01“新增年级限定报名”、CR-02“新增邮件通知”
- **不变范围**：P2-F01—P2-F08 的既有行为、C1—C10 验收口径、现有部署方式与数据库选型

---

## 1. 结论摘要

| 项目 | 结论 |
|---|---|
| CR-01 设计方向 | 沿现有“报名策略”扩展：策略接口改为接收 `RegistrationContext`，新增 `GradeLimitedDirectRegistrationPolicy` |
| CR-02 设计方向 | 沿现有“观察者”扩展：新增 `EmailNotificationObserver`，不改 `RegistrationService` 与事件发布器 |
| 预计新增类 | 9 个（CR-01 3 个、CR-02 6 个） |
| 预计修改核心业务类 | 3 个：`RegistrationService`、`RegistrationPolicy`、`RegistrationPolicyFactory`；另需同步 2 个既有策略实现 |
| 预计新增变更用例 | 10 个（CR1-01—04、CR2-01—04，另加组合/失败用例） |
| 回归范围 | 现有 15 项测试全部重跑，C1—C10 逐条确认；实施后共 24 项 |
| 最高风险 | 策略接口签名变更、老库 `student.grade` 迁移、直接报名事件语义（`SUBMITTED + APPROVED`） |
| 明确不做 | 真实邮件服务、MQ、outbox、重建项目、范围外功能 |

**总体判断**：两项 CR 都能落在现有两个扩展点上，不需要推翻 V1 架构。CR-01 需要一次受控的接口演进；CR-02 基本是“只加观察者”的增量改造。主要工作量在数据迁移、前端策略分支和回归证据，而不是重写业务主流程。

## 2. 基线事实

### 2.1 现有结构

- 后端：Spring Boot 3.3.5 + Java 21 + MyBatis，包名 `com.Cynyun.campusevent`。
- 前端：Vue 3 + Vite + Element Plus，构建产物放入 Spring Boot 的 `src/main/resources/static`。
- 默认 SQLite，可切换 MySQL；SQLite 单连接池，事务内用 `SELECT ... FOR UPDATE` 语义锁活动行。
- 分析时生产 Java 文件 52 个；测试 15 项（验收 10、重启持久化 1、策略 3、密码 1）。实施后生产 Java 61 个，测试 24 项。

### 2.2 现有策略与事件

```java
public interface RegistrationPolicy {
    RegistrationStatus decide(int approvedCount, int capacity);
}
```

- `DirectRegistrationPolicy`：满员抛 `BusinessException.conflict("活动名额已满")`，否则 `APPROVED`。
- `ApprovalRegistrationPolicy`：始终 `PENDING`。
- `RegistrationPolicyFactory`：按 `PolicyType.DIRECT / APPROVAL` 返回策略。
- `RegistrationService.register`：锁活动 → 校验删除/开始时间/重复报名 → 统计已通过人数 → 调策略 → 插入报名 → `afterCommit` 发布事件。
- `RegistrationEventPublisher`：遍历 `List<NotificationObserver>`，逐个 `try/catch`，单个观察者异常不影响其他观察者，也不回滚事务。
- `InAppNotificationObserver`：按事件类型写站内 `Message`。

### 2.3 现有数据模型缺口

- `Student` 只有 `studentId, name, passwordHash`，没有 `grade`。
- `Activity` 有 `policyType`，但没有年级上下限字段。
- 数据库脚本全部使用 `CREATE TABLE IF NOT EXISTS`：**已有库不会因为改脚本自动增加列**。
- 没有 `email_log` 表，也没有邮件发送抽象。

### 2.4 现有前端策略分支

- `utils/format.js` 的 `policyText` 只判断 `APPROVAL`，其余一律显示“直接报名”。
- `activityState` 只对 `DIRECT` 判断满员，新增枚举会被误判为“报名中”。
- `ActivityFormView.vue` 只有“直接报名 / 审核制”两个单选项。
- `ActivityListView.vue` 的筛选下拉只有两个选项。
- `ActivityDetailView.vue` 的 `canRegister` 只对 `DIRECT` 检查容量，其他类型直接允许。
- `PolicyTag.vue`、管理员活动列表复用上述格式化函数。

> 结论：新增 `GRADE_LIMITED_DIRECT` 后，前端不是“自动兼容”，必须逐处补分支，否则会出现“标签写成直接报名、详情页按钮逻辑错误、满员状态不显示”的假通过。

## 3. CR-01：年级限定报名

### 3.1 需求拆解

| 要点 | 影响 |
|---|---|
| `Student` 增加 `grade`，取值 1—4 | 实体、Mapper、建表脚本、老库迁移、演示数据 |
| 新增“年级限定直接报名”活动类型 | `PolicyType` 增加枚举值，管理端可创建 |
| 仅大二、大三可报名 | 新增策略内校验，非 2/3 返回 403 与明确文案 |
| 仍遵守名额、开始时间、重复报名 | 复用现有锁、查重、容量检查，不另写一套 |
| 原有直接报名/审核报名行为不变 | C1—C10 必须全量回归 |

### 3.2 设计选择

**推荐方案 A：策略上下文 + 新策略**

- 把 `RegistrationPolicy` 改为单一入口：

```java
RegistrationStatus decide(RegistrationContext context);
```

- 新增：

```java
public record RegistrationContext(
        Student student,
        Activity activity,
        int approvedCount
) {}
```

- 新增 `GradeLimitedDirectRegistrationPolicy`：
  1. 年级为空或不在 1—4：`forbidden("年级信息异常，请联系管理员")`；
  2. 年级不在 2/3：`forbidden("该活动仅限大二、大三学生报名")`；
  3. 已通过人数达到容量：`conflict("活动名额已满")`；
  4. 否则返回 `APPROVED`。
- `RegistrationPolicyFactory` 增加 `GRADE_LIMITED_DIRECT` 分支。
- `RegistrationService.register` 注入 `StudentMapper`，先查学生，再构造上下文；锁、查重、计数、插入、发布的主流程不变。
- 现有两个策略改为从上下文取 `approvedCount / capacity`，行为不变。

**为什么推荐 A**

- 年级是“报名准入”的一部分，放在策略轴内语义完整，不把规则拆到服务层。
- 现有设计文档已预留“策略需要额外数据时应引入上下文对象”，这次正好兑现，不需要发明第二套扩展机制。
- 只改一个接口切口；新增策略与既有策略并列，后续再加“仅研究生”“仅新生”时仍是同一扩展点。

**方案 B：可组合资格规则（不推荐）**

- 在服务层增加 `List<RegistrationEligibilityRule>`，年级规则单独实现。
- 问题：`GRADE_LIMITED_DIRECT` 仍然是策略类型，但它的核心限制却不在策略里；“报名类型”和“资格规则”两个扩展点会交叉，规则顺序、组合、错误文案都变复杂。对本次单一规则来说，抽象成本高于收益。

**方案 C：服务里写 if/else（不推荐）**

- 改动最少，但每加一种报名类型都要改核心服务，直接违背 V1 用策略隔离变化点的初衷。

**方案 D：保留旧 `decide(int,int)` 重载做桥接（不推荐）**

- 旧签名没有年级，年级策略被旧入口调用时只能抛错或静默放行，两个入口的语义不一致。应一次性把接口收敛到上下文入口。

### 3.4 数据迁移与兼容

- 新库：`student.grade INTEGER`，允许为空，应用层校验 1—4。
- 老库：`SchemaMigration` 用 `DatabaseMetaData` 检查列是否存在，不存在才执行 `ALTER TABLE student ADD COLUMN grade INTEGER`；重复启动安全。用 `ApplicationRunner` + `@Order` 保证迁移先于 `DemoDataSeeder`。
- 演示数据建议：`student`（演示学生）`grade=2`；`student01=1`、`student02=2`、`student03=3`、`student04=4`，其余循环 1—4。这样 CR1 的四个年级用例都有稳定账号。
- `Activity` 本期不加 `minGrade/maxGrade`：CR 明确只限大二/大三，固定 `{2,3}` 放在策略里；若后续要求管理员自选年级，再加字段，不在本次提前设计。
- 现有登录用户不暴露 `grade`：前端只按容量决定按钮是否可点，年级是否符合由后端策略判断，403 文案直接展示；避免把权限判断复制到前端。如后续要在页面显示“你的年级”，再扩展 `LoginUser`。

### 3.5 测试映射

| 用例 | 场景 | 预期 |
|---|---|---|
| CR1-01 | `student02`（grade=2）报年级限定活动 | 200，`APPROVED` |
| CR1-02 | `student03`（grade=3）报名 | 200，`APPROVED` |
| CR1-03 | `student01`（grade=1）报名 | 403，文案含“仅限大二、大三” |
| CR1-04 | `student04`（grade=4）报名 | 403，文案含“仅限大二、大三” |
| CR1-05 | 重跑 C1—C10 | 全部通过，原有直接/审核行为不变 |

补充单测：年级为空、年级越界、满员时年级合格学生仍被 409 拒绝、满员时低年级学生优先返回年级 403（顺序需固定并写清）。

### 3.6 风险与缓解

| 风险 | 缓解 |
|---|---|
| 接口签名变更导致编译面扩大 | 一次性改两个实现与测试，不保留旧重载；IDE 编译错误即清单 |
| 老库没有 `grade`，启动查询失败 | 迁移在 MyBatis 首次查询前执行；启动日志打印迁移结果 |
| 新枚举被前端误判 | 逐处补 `format.js`、表单、筛选、详情、管理员列表，并截图复验 |
| 测试学生没有年级 | 验收测试 `@BeforeAll` 插入时补 `grade`，不依赖演示数据 |
| 规则顺序导致错误文案 | 先年级、后容量；单测固定顺序，避免“满员但提示年级”歧义 |

## 4. CR-02：邮件通知

### 4.1 需求拆解

| 要点 | 影响 |
|---|---|
| 站内通知保留，新增模拟邮件 | 新增观察者，不替换原观察者 |
| 记录收件人、主题、内容、状态、时间 | 新增 `email_log` 表与实体/Mapper |
| 不接真实邮件 | `MockEmailSender` 模拟，不引入 SMTP 依赖 |
| 邮件失败不回滚报名 | 复用 `afterCommit` + Publisher 的异常隔离 |
| 同一业务事件不重复发送 | 复用状态机 409；不新增幂等键，但记录崩溃窗口 |
| 不把邮件代码写进 `RegistrationService` | 只加观察者，Service 零修改 |

### 4.2 设计选择

**推荐方案：新增 `EmailNotificationObserver`**

```java
public interface EmailSender {
    void send(EmailMessage message);
}
```

- `EmailMessage`：`registrationId, eventType, recipient, subject, content`。
- `MockEmailSender`：写 `email_log`，状态 `SENT`；当 `app.mock-email.fail=true` 时写 `FAILED + error_message` 后抛出，供 CR2-03 验证。
- `EmailNotificationObserver implements NotificationObserver`：过滤事件、查活动标题、组装邮件、调用 `EmailSender`。
- `EmailLog` + `EmailLogMapper` + XML：落库。
- `email_log` 表：`id, registration_id, event_type, recipient, subject, content, status, error_message, created_at`。

**为什么这是最小改动**

- `RegistrationService`、`RegistrationEventPublisher`、`NotificationObserver` 均不需要改；现有观察者列表会自动发现新 Bean。
- 邮件失败由 Publisher 统一 catch，天然满足“不回滚报名”；不需要在业务层加 try/catch。
- 站内与邮件是两个独立观察者，任一失败不影响另一个。

### 4.3 事件过滤

| 业务动作 | 事件 | 站内 | 邮件 |
|---|---|---|---|
| 直接报名通过 | `SUBMITTED + APPROVED` | 报名成功 | 报名成功 |
| 审核报名提交 | `SUBMITTED + PENDING` | 等待审核 | 不发 |
| 审核通过 | `APPROVED` | 报名已通过 | 报名已通过 |
| 审核拒绝 | `REJECTED` | 报名未通过 | 报名未通过 |
| 取消报名 | `CANCELLED` | 报名已取消 | 不发 |

> 关键点：直接报名成功的事件类型是 `SUBMITTED`，状态是 `APPROVED`；如果只判断 `type == APPROVED`，会漏掉直接报名邮件。这是 CR2 最容易写错的地方。

### 4.4 失败与重复

- 失败：`MockEmailSender` 先写 `FAILED` 日志再抛出；Publisher 捕获后继续，事务已提交，报名状态不受影响。
- 重复：重复报名、重复审批、重复拒绝、重复取消都会被现有状态机以 409 挡住，不会产生第二个事件。
- 已知窗口：若进程在 `afterCommit` 之后、邮件落库之前崩溃，可能“报名成功但没有邮件”。本期不引入 outbox/重试，报告如实说明；这属于实验范围内的已知限制。

### 4.5 新增与修改清单

| 文件/位置 | 类型 | 变更 |
|---|---|---|
| `mail/EmailNotificationObserver.java` | 新增 | 实现 `NotificationObserver`（实际落在 mail/ 包） |
| `mail/EmailSender.java` | 新增 | 发送抽象 |
| `mail/MockEmailSender.java` | 新增 | 模拟发送 + 失败开关 |
| `mail/EmailMessage.java` | 新增 | 邮件数据 |
| `entity/EmailLog.java` | 新增 | 日志实体 |
| `mapper/EmailLogMapper.java` + XML | 新增 | 写日志 |
| `resources/schema-sqlite.sql`、`schema-mysql.sql` | 修改 | 新增 `email_log`，`CREATE TABLE IF NOT EXISTS` |
| `application.yml` | 修改 | 增加 `app.mock-email.fail` 默认 `false` |
| `tests/.../CampusEventAcceptanceTest.java` | 修改 | 新增 CR2 用例 |

### 4.6 测试映射

| 用例 | 场景 | 预期 |
|---|---|---|
| CR2-01 | 直接报名通过 | 站内消息 + 邮件日志各 1 条，状态 `SENT` |
| CR2-02 | 审核批准 / 拒绝 | 两渠道分别有对应结果记录 |
| CR2-03 | 打开模拟失败开关后报名 | 报名仍成功；`email_log` 为 `FAILED`，含错误信息 |
| CR2-04 | 重复提交同一审批 | 第二次 409；邮件日志不增加 |
| CR2-05 | 重跑 C1—C10 | 全部通过，原站内通知不变 |

### 4.7 风险与缓解

| 风险 | 缓解 |
|---|---|
| 直接报名事件被漏发 | 观察者按 `(type,status)` 组合判断，单测覆盖 `SUBMITTED+APPROVED` |
| 邮件失败影响主流程 | 复用 Publisher 的 try/catch；测试断言报名仍成功 |
| 重复发送 | 状态机 409 + 用例 CR2-04；文档说明崩溃窗口 |
| 收件人没有真实邮箱 | 统一用 `studentId + "@campus.example"` 模拟地址；如教师要求真实邮箱，再补 `Student.email` |
| 日志无限增长 | 课程项目不清理，文档注明；生产化再加归档策略 |
| 观察者顺序不确定 | 两个观察者互不依赖；测试只断言最终结果，不依赖执行顺序 |

## 5. 跨变更回归与部署

### 5.1 回归重点

- C1—C10 全量重跑，重点确认：
  - 原有 `DIRECT` 直接报名仍即时 `APPROVED`；
  - 原有 `APPROVAL` 仍先 `PENDING`，审批后 `APPROVED/REJECTED`；
  - 重复报名、满员、取消、统计、站内消息数量不变；
  - 重启后数据仍在。
- 新增用例与原有 15 项一起跑；实施后实际为 **24 项全部通过**（旧 15 + 新增 9）。
- 前端复验：活动创建、列表筛选、详情报名、满员提示、年级拒绝提示、管理员标签，逐页截图。

### 5.2 构建与部署

1. 后端：`mvn test` 与 `mvn -DskipTests package`，确认 24 项通过。
2. 前端：`npm run build`，将 `dist` 复制到 `campusevent-server/src/main/resources/static`。
3. 重新打包并上传服务器，保留旧 jar 备份。
4. 线上验证：首页 200、student/admin 登录 200、年级限定活动可见、低年级报名 403、合格年级报名 200、邮件日志有记录。
5. 打标签 `change-v2`，保留 `baseline-v1` 不删除。

### 9.2 与分析不一致的地方

- `EmailNotificationObserver` 实际放在 `mail/` 包，而不是分析稿写的 `event/`；它实现的仍是 `NotificationObserver` 接口，包位置按“邮件能力聚合”调整。
- 变更用例最终没有单独做 10 个验收方法：CR1-01—04 合并为 1 个验收测试内的四个账号断言，CR2-01/02/04 合并为 1 个验收测试，CR2-03 拆为独立邮件失败集成测试；可读性与回归速度优先，覆盖点未减少。
- 前端只做 4 个文件的分支补齐，没有新增页面；管理员列表与标签复用 `format.js`，因此不需要单独改组件。
- `SchemaMigration` 用 `SELECT COUNT(grade) FROM student` 判断列是否存在，而不是分析稿写的 `DatabaseMetaData`；SQLite 与 MySQL 都能执行，逻辑更短。
- 实际没有新增 `app.mock-email.fail` 之外的邮件配置；真实 SMTP 仍未接入。

### 9.3 验证与遗留

- 本地自动化：24 项全部通过；前端 `npm run build` 成功，`dist` 已复制到 `campusevent-server/src/main/resources/static`。
- 线上验证：部署后补记；需覆盖 student/admin 登录、年级限定活动创建与筛选、四个年级报名结果、`email_log` 的 SENT/FAILED 记录、CORS。
- 仍未做：真实 SMTP、outbox/重试、MySQL 全量回归、前端自动化、并发压测。以上均写入 README 与回归测试表的缺口，不把“模拟邮件通过”说成“邮件系统完成”。

### 9.4 结论修正

两项 CR 都落在 V1 预留的策略与观察者扩展点上，没有推翻架构；真正的成本集中在接口签名连锁修改、老库迁移、前端枚举分支与证据整理，而不是主流程重写。分析阶段“最小改动”的判断成立，但对测试方法数的估算偏乐观：合并验收断言后，新增用例数为 9 而不是 10。

| 是否在登录信息中暴露年级 | 不暴露 | 前端只显示后端 403 文案 |
| 取消报名是否发邮件 | 不发 | CR 只要求通过/拒绝 |
| 待审核是否发邮件 | 不发 | CR 只要求通过/拒绝 |
