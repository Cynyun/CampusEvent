# CampusEvent 设计模式决策报告（初始版 V1）

**项目**：校园活动报名与管理系统（CampusEvent）  
**对应基线**：baseline-v1（初始版，教师 CR 发布前）  
**编写日期**：2026-11-23  
**适用范围**：报名准入策略、报名结果通知两条变化轴；不覆盖前端组件、持久化框架和部署方案  
**证据**：源码、设计文档 02—05、C1—C10 自动化测试、docs/回归测试表.md

> 本报告回答四个问题：为什么这里需要模式、为什么选这个模式、模式在代码里如何落地、采用后付出什么代价。报告不把“用了策略/观察者”当作结论，而是把“变化点在哪里、边界怎么划、哪些事模式不负责”写清楚。

## 1. 问题背景与变化点

CampusEvent 的报名有两条业务规则：

- 直接报名：名额未满时立即通过，名额已满时拒绝。
- 审核型报名：先进入待审核，管理员批准时再检查名额。

如果只在 RegistrationService 里写 if/else，第一版能跑，但会出现三个问题：

1. **新增报名方式要改服务**：每加一种规则都要在 register 里加分支，违反“对扩展开放、对修改关闭”。
2. **规则与流程混在一起**：锁活动、查重、算名额、决定状态、写通知都在一个方法里，测试只能整段测，难以单独验证“满员时直接报名应拒绝”。
3. **通知与业务耦合**：报名、取消、批准、拒绝四个动作都要写站内消息，如果每处直接调 messageMapper.insert，通知失败是否回滚、以后加短信/邮件是否要改四个方法，都会变成隐性问题。

因此识别出两条独立变化轴：

| 变化轴 | 变化内容 | 稳定部分 | 适合的模式 |
|---|---|---|---|
| 报名准入规则 | 直接通过 / 审核后决定 / 未来可能增加候补、白名单 | “提交一条报名并得到初始状态”的流程 | 策略 Strategy |
| 报名结果通知 | 站内消息 / 未来邮件、短信、审计日志 | “某个报名事件发生后通知关心它的人” | 观察者 Observer |

两条轴彼此独立：新增报名方式不应改通知代码，新增通知渠道也不应改报名规则。这决定了不能用一个大而全的“报名管理器”同时承担两件事。

## 2. 决策一：报名准入用策略模式

### 2.1 备选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 服务内 if/else | register 中按 policyType 分支 | 最少类、最直观 | 每加规则改服务；分支与锁/查重/通知混在一起；难单独测规则 | 否 |
| B. 策略接口 + 工厂 | 每种规则一个类，服务依赖接口 | 新增规则只加类；规则可单测；服务流程稳定 | 多一层抽象；策略需要上下文参数 | **采用** |
| C. 策略同时负责审批 | 策略既决定提交状态，也决定批准/拒绝 | 规则集中 | 审批是带锁、带复查的命令，不是“新提交”；策略会依赖 Registration/锁，职责膨胀 | 否 |
| D. 规则引擎/脚本 | 外置规则表或 DSL | 业务人员可改 | 课程项目无运维支撑；调试与测试成本高 | 否 |

### 2.2 结构

- RegistrationPolicy：抽象策略，只有一个方法 decide(int approvedCount, int capacity)，返回 RegistrationStatus。
- DirectRegistrationPolicy：具体策略，容量足够返回 APPROVED，否则抛 BusinessException.conflict(“活动名额已满”)。
- ApprovalRegistrationPolicy：具体策略，始终返回 PENDING；满员也允许提交，因为待审核不占名额。
- RegistrationPolicyFactory：根据 PolicyType（DIRECT/APPROVAL）返回对应单例组件；非法类型抛参数异常。
- RegistrationService：依赖 RegistrationPolicyFactory，不依赖具体策略类。

类关系是“服务 → 工厂 → 策略接口 ← 具体策略”。服务只知道“我要一个能决定初始状态的策略”，不知道具体是哪一个。

### 2.3 运行时序（直接报名）

1. 学生提交报名，RegistrationService.register 开启事务。
2. 锁定活动行（MySQL 为 SELECT ... FOR UPDATE；SQLite 由单连接池串行化）。
3. 校验活动存在、未删除、尚未开始；查询是否已有 PENDING/APPROVED 的有效报名。
4. 统计当前 APPROVED 数量。
5. 工厂按 activity.policyType 返回策略；策略用 approvedCount 与 capacity 决定 APPROVED 或抛满员冲突。
6. 插入 Registration；事务提交后发布 SUBMITTED 事件，观察者写站内通知。

审核型报名的差异只在第 5 步：策略始终返回 PENDING；提交阶段不检查容量，因此 PENDING 不占名额。

### 2.4 名额检查为什么这样划分

这是本设计最容易被质疑的地方，单独说明。

设计文档的总体表述是“策略只决定报名结果，容量、开放时间、重复报名由 RegistrationService 统一校验”。落地时进一步细化为三层：

| 职责 | 归属 | 原因 |
|---|---|---|
| 锁定活动、统计 APPROVED、保证并发下不超卖 | RegistrationService + Mapper | 这是跨用例的公共不变量，不应由某个策略各自实现 |
| 决定“新提交”得到 APPROVED 还是 PENDING | RegistrationPolicy | 这是两种报名方式真正不同的地方，也是最常变化的地方 |
| 批准时再次检查容量，满员不得批准 | RegistrationService.approve | 批准是审批命令，不是新提交；它必须复查同一个容量上限，不能交给“提交策略”决定 |

因此，DirectRegistrationPolicy 虽然接收 approvedCount 并做比较，但它消费的是服务已经统计好的值，不负责加锁、不负责查重、不负责审批；容量上限的最终守卫仍在服务层。这样既让“直接报名满员拒绝”成为可单测的策略行为，又没有把并发安全和审批不变量下放给策略。

需要如实说明的偏差：设计评审阶段写的是“容量由服务统一校验”，实现阶段把“提交准入判定”放到了策略里。两者不是互相否定，而是把“统计与锁”和“准入判定”拆开；但如果评审教师要求“策略完全不接触容量”，则需要把 decide 改为无参并让服务在调用前分支，这会削弱策略的意义，属于可讨论的设计取舍，不应在报告里掩盖。

### 2.5 采用后的效果

**收益**

- 新增规则（例如候补）只需新增策略类与工厂分支，register 主流程不变。
- DirectRegistrationPolicy 可用纯单元测试覆盖“有余量/满员”两个分支，不必启动 Spring 或数据库；现有 RegistrationPolicyTest 的 3 个用例即是这一收益的证据。
- 服务代码只出现一次 policy.decide(...)，没有按类型展开的 if/else，阅读路径短。

**代价**

- 多出 4 个类和一个工厂；对只支持两种规则的项目来说，类数量偏多。
- 策略需要 approvedCount/capacity 两个参数；如果未来规则需要“学生历史”“活动分类”等上下文，就要引入上下文对象，接口会变宽。
- 工厂目前是 switch，新增枚举值必须同步修改工厂；这是“集中式创建”的代价，但比把分支散在服务里更可控。
- 策略抛 BusinessException 表达了“满员”，这使策略依赖 Web 层的异常语义；更纯粹的做法是返回结果对象，由服务转异常。当前为了少一层映射接受这个耦合，属于课程规模下的取舍。

### 2.6 扩展方式

新增“候补报名”时：

1. 在 PolicyType 增加 WAITLIST；
2. 新增 WaitlistRegistrationPolicy 实现 RegistrationPolicy；
3. 在 RegistrationPolicyFactory 增加分支；
4. 前端报名方式下拉增加选项；
5. 补策略单测与一条验收用例。

RegistrationService.register 的锁、查重、插入、事件发布均不需要改。若新规则需要额外数据，应新增一个 RegistrationContext 参数，而不是让策略直接查库；否则策略会从“纯决策”退化为“带持久化的服务”，工厂也会难以测试。

## 3. 决策二：结果通知用观察者模式

### 3.1 备选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 服务内直接写消息 | 每个业务方法末尾调 messageMapper.insert | 最简单、链路最短 | 四个业务方法重复；加渠道要改四处；通知异常与业务事务混在一起 | 否 |
| B. Spring ApplicationEvent | 发布事件，@EventListener 或 @TransactionalEventListener 接收 | 框架原生、少写发布器 | 事件类型与监听器注册由容器管理；多监听器异常传播默认会影响发布者，需要额外配置；课程中不易展示“逐个隔离失败” | 备选 |
| C. 自定义发布器 + 观察者接口 | 业务发布 RegistrationEvent，发布器遍历 List<NotificationObserver> | 结构显式；每个观察者异常可单独隔离；易单测 | 需要自己写发布器和事务钩子；要注意注册/注销 | **采用** |
| D. MQ | 业务发消息到队列，消费者写通知 | 削峰、可靠、可重试 | 需要中间件与运维；课程项目过重 | 否 |

选择 C 而不是 B 的理由：本项目要展示“业务对象不依赖通知实现”的结构，并且要在通知失败时明确“只记日志、不回滚业务”。自定义发布器把这两点写成可见代码；Spring 事件也能做到，但需要额外理解监听器异常策略，对评审展示不如显式结构直观。

### 3.2 结构

- RegistrationEvent：事件数据，包含 type、status、registrationId、studentId、activityId、occurredAt。
- RegistrationEventPublisher：注入 List<NotificationObserver>，逐个调用 onEvent；每个观察者包在 try/catch 中，失败 log.warn，继续下一个。
- NotificationObserver：观察者接口，只有一个 onEvent(RegistrationEvent)。
- InAppNotificationObserver：站内消息观察者，按事件类型生成文案并插入 Message。
- TransactionHooks：把“发布”挂到事务提交之后；没有事务时立即执行。

### 3.3 通知失败是否影响事务

不影响已经提交的业务事务。原因有三点：

1. publishAfterCommit 在事务提交后才执行，观察者运行时业务数据已经落库；此时抛异常也无法回滚已提交事务。
2. RegistrationEventPublisher 对每个观察者单独 try/catch，只记录 warn，不向调用方抛出。
3. 通知写入不参与业务事务的原子提交；即使消息插入失败，Registration 仍然有效。

代价是“业务成功、通知缺失”。当前没有 outbox、没有重试、没有死信队列；这是明确接受的限制（U2）。如果教师 CR 要求通知可靠，正确做法是引入 outbox 表：业务事务内写 outbox，独立任务重试投递，观察者消费成功后标记；而不是在业务方法里同步重试。

### 3.4 如何避免重复通知

当前依靠“状态机前置条件 + 只发布一次”：

- 重复报名在 register 阶段被 409 拒绝，不会产生第二个 SUBMITTED 事件。
- 重复批准在 approve 阶段要求状态仍为 PENDING；已 APPROVED 的再次批准返回 409，不发布事件。
- 重复取消要求状态为 PENDING/APPROVED；已 CANCELLED 的再次取消返回 409，不发布事件。
- 发布器不做重试，因此不会因重试本身产生重复消息。

但必须承认：当前没有幂等键、没有消息去重表。若同一请求在“业务提交成功、响应丢失”后被客户端重试，状态机通常会挡住第二次操作；若进程在 afterCommit 执行到一半崩溃，可能出现“部分观察者已写、部分未写”，也可能在人工重放时重复。由于目前只有一个站内观察者，这个窗口很小，但不是一个可宣称“绝不重复”的设计。报告按实际写，不把“没有重试”说成“已经幂等”。

### 3.5 采用后的效果

**收益**

- RegistrationService 的四个业务方法只调用 publishAfterCommit，不 import MessageMapper，不知道通知长什么样。
- 新增邮件/短信观察者只需实现接口并注册为组件，业务方法不改。
- 每个观察者失败互不影响；日志能定位是哪个 registration、哪个事件类型失败。
- 事件对象携带 studentId/activityId，观察者不需要反查业务对象，耦合低。

**代价**

- 多出 4 个类和一个事务钩子；对只有一种通知渠道的项目偏重。
- 事件是进程内同步调用，观察者慢会拖慢请求；当前站内插入很快，未做异步。
- 观察者列表由 Spring 注入，属于启动时固定；当前没有动态注册/注销需求。若未来支持运行时插拔，必须提供 unregister，否则监听器会泄漏——这是观察者模式的经典代价，不能只写“松耦合”而不写注销。
- 没有幂等与重试，可靠性是“尽力而为”，不是“至少一次”。

### 3.6 扩展方式

新增邮件观察者：

1. 新建 EmailNotificationObserver 实现 NotificationObserver，加 @Component；
2. 在 onEvent 中按 type 生成邮件内容；
3. 不修改 RegistrationService、RegistrationEventPublisher；
4. 补一条“邮件失败不影响报名”的集成测试。

若观察者需要按事件类型过滤，可在观察者内部判断，或在发布器增加 supports(event) 的默认方法；不要在发布器里写具体渠道的 if/else，否则观察者模式会退化为“发布器知道所有实现”。

## 4. 两个模式如何协作

一次“审核型报名被批准”的完整链路：

1. 管理员调用 approve；RegistrationService 开启事务，锁活动、锁报名。
2. 校验状态为 PENDING；统计 APPROVED；若满员抛 409，不改变状态。
3. 更新为 APPROVED；构造 APPROVED 事件；注册 afterCommit 回调。
4. 事务提交；TransactionHooks 触发发布器。
5. 发布器遍历观察者；InAppNotificationObserver 写“报名已通过：《活动名》”。
6. 若写消息失败，发布器 catch 并 log.warn；接口仍返回成功，报名保持 APPROVED。

策略在第 2 步之前已经决定了“提交时是 PENDING”；审批阶段的容量复查由服务完成。观察者只消费“已经发生的事实”，不参与状态决策。三者边界清晰：策略决定准入，服务守护不变量，观察者传播结果。

## 6. 代价与不适用场景

- 如果项目永远只有“直接报名”一种规则，策略模式是过度设计；一个 if 足够。本项目采用它，是因为指导书明确要求两种报名方式，且 CR 可能增加规则。
- 如果通知必须可靠、必须审计、必须跨进程，当前进程内观察者不够；应上 outbox + MQ，而不是继续加观察者。
- 如果规则需要大量外部数据或频繁热更新，纯策略类不够；需要规则引擎或配置化，但会带来调试与治理成本。
- 如果团队不熟悉事务提交后回调，afterCommit 的时机容易被误解为“方法返回后”；代码和报告都要明确它是“事务提交后、响应返回前”。

| 指标 | 结果 | 说明 |
|---|---|---|
| 生产 Java 文件 | 52 个 | 含 controller/service/mapper/policy/event/config 等 |
| 策略相关类 | 4 个 | 接口、两个实现、工厂 |
| 事件相关类 | 4 个 | 事件、发布器、观察者接口、站内观察者 |
| 自动化测试 | 15 项全部通过 | C1—C10 共 10 项、真实重启 1 项、策略单测 3 项、密码单测 1 项 |
| C1—C10 覆盖 | 全部通过 | 见 docs/回归测试表.md |
| 通知失败回滚 | 未发生 | 观察者异常被 catch；但未做故障注入测试，属于待补证据 |
| 并发不超卖 | 逻辑上由行锁保证 | MySQL 行锁；SQLite 单连接；未做高并发压测 |

“通知失败不回滚”目前是代码结构保证，不是故障注入实测；如果评审要求实证，应增加一个抛异常的测试观察者，验证接口仍成功且日志有 warn。这一点应在后续补测，不应把“代码看起来会 catch”当成“已经验证”。

## 8. 结论

- 报名准入选策略模式，是因为“报名方式”是明确、可枚举、会扩展的变化点；服务依赖工厂与接口，新增规则不改主流程。
- 通知选观察者模式，是因为“一个报名事件、多个潜在渠道”是典型一对多关系；发布器隔离每个观察者的失败，业务不被通知拖垮。
- 两个模式都不负责并发、事务和状态机；这些仍由 RegistrationService 与数据库锁承担。模式解决的是“变化点隔离”，不是“所有质量问题”。
- 当前设计在课程规模下成立；若 CR 提出可靠通知、候补队列或复杂审批链，应先做影响分析，再决定是扩展策略/观察者，还是引入 outbox、状态机或规则引擎，避免为了“继续用模式”而扭曲需求。
